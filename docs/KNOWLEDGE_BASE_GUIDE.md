# Руководство по редактированию базы знаний

База знаний — обычные TypeScript-файлы с данными в `src/domain/kb/`. Движок менять не нужно: добавить состояние или симптом = добавить данные + правила. Типы проверяются при `npm run build`, инварианты — тестами `npm test`.

## Соглашения о находках (findings)

- boolean-симптом: «да» → находка `<id>`; «нет» → `<id>::no` (явное отрицание).
- choice-опция: массив `findings` опции (может быть пустым только для опций «Неизвестно»).
- number-симптом: диапазоны `ranges` (пороги стекаются — 41,2 °C дает и fever, и high-fever).
- Факторы анамнеза: `findings` опций; «Неизвестно» = пустой массив.
- Находка может использоваться несколькими состояниями; каждое правило — отдельная ассоциация.

## Добавить симптом

1. В `src/domain/kb/symptoms.ts` добавить объект с уникальным `id`, `system` (одна из 9 систем), `label` (RU, наблюдательный), опционально `hint` и `ageBands`.
2. При необходимости добавить ассоциации в `src/domain/kb/rules.ts`.
3. `npm test` — проверит уникальность ID и разрешимость находок.

## Добавить состояние (дифференциал)

1. В `conditions.ts`: `id`, `name`, `category`, `description` (RU, без лечения), `ageWindow {min,max}` (типичное окно!), `confidence`, `zoonotic`, `prior` (0–1.5, только для сортировки), `reviewStatus`.
2. В `rules.ts`: минимум 2 поддерживающие ассоциации (вес 1–5); при необходимости «против»-правила и взаимодействие.
3. Если состояние зоонозное — описание должно содержать слова «человек»/«гигиена» (тест).

## Веса: как выбирать

| Вес | Смысл | Пример |
|---|---|---|
| 5 | практически патогномоничный паттерн в контексте | припухший сустав → joint ill |
| 4 | сильная характерная связь | водянистая диарея → криптоспоридиоз |
| 3 | выраженная, но неспецифичная связь | лихорадка → сальмонеллез |
| 2 | умеренная поддержка | групповое содержание → BRD |
| 1 | слабый фоновый вклад | мокнутие пупка → omphalitis |

Веса — экспертные оценки для детерминированного скоринга, **не вероятности** и пользователю не показываются.

## Возрастные множители

`ageMultipliers` в ассоциации умножают поддерживающий вес в конкретной возрастной группе (напр., водянистая диарея ×1,25 в 8–21 день для криптоспоридиоза). Жесткое отсечение по возрасту делает `ageWindow` состояния, не множители.

## Красные флаги и гейты

- **Red flag** (`triage.ts` redFlags): `allOf` (все находки) + `anyOf` (хотя бы одна, если непусто) + опциональные `ageBands` → сообщение в emergency-баннер. Формулировка: признак + «немедленно к специалисту», без самолечения.
- **Severity gate**: тот же паттерн соответствия, но `floor` — минимальный уровень срочности (`urgent`/`prompt`) с причиной. Гейт никогда не понижает уровень, установленный red flag.
- Правило: сомневаетесь между gate и red flag — выбирайте red flag (перестраховка безопаснее).

## Пороги числовых значений

Каждый диапазон обязан содержать `basis` со строкой `needs-veterinary-review:` до прохождения ветревью (тест проверяет температуру). После валидации замените текст на ссылку/описание источника.

## Rule-out заметки

`ruleOuts` — статические подсказки без скоринга: `whenFindings` → показ. Используйте для «второстепенных» состояний (грыжа, лишай, родовая травма), чтобы не раздувать скоринговую модель.

## Версионирование и статус

1. Изменили контент → поднимите `KB_VERSION` (semver: клиника = minor, правки текстов = patch) и `KB_DATE` в `kb/index.ts`.
2. `reviewStatus` на элементе: `draft` → `pending-review` → `vet-approved` (после чек-листа).
3. Общий статус БЗ (`kb.reviewStatus`) = `vet-approved` только после полного прогона `docs/VETERINARY_REVIEW_CHECKLIST.md`.
4. Опишите изменение в `CHANGELOG.md`.
5. Обновление доезжает до пользователей автоматически: БЗ входит в precache service worker.

## Что нельзя делать

- Не ссылайтесь на источники, которые не можете проверить.
- Не добавляйте лечения, дозировки, протоколы — это out-of-scope (см. docs/DISCLAIMER.md).
- Не делайте выводы «цвет кала → возбудитель» — наблюдения без интерпретации.
- Не используйте проценты вероятностей — движок показывает только категории.
